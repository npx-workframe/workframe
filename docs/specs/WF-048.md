# WF-048 — Capability-based credential lifecycle

## Purpose

Workframe may use provider authority without exposing the upstream secret or OAuth token through normal product authority: browser APIs, ordinary users, workspace administrators, application-level stack operators, agent prompts, profile files, logs, receipts, or runtime tools.

This is a product-boundary guarantee, not a claim against host/root compromise. A person who controls the host, API container, process memory, vault database, and KEK boundary can ultimately observe provider authority because the API must decrypt or present it for outbound requests. Workframe must minimize and audit that trust, but it cannot honestly call the host boundary zero-knowledge.

The current envelope-encrypted vault and opaque lease design is the correct base. This rail tightens it; it does not replace it with crypto theater, a new secret manager, blockchain, MPC, enclaves, or a local-only architecture.

## Invariants

1. One credential binding ID owns one provider authority record and one monotonically increasing capability generation.
2. Raw API secrets and refresh/access tokens are materialized only inside the narrow outbound provider-auth path and are never returned as product data.
3. Runtime files contain opaque Workframe capabilities and nonsecret provider metadata only. No upstream API key, access token, refresh token, authorization code, session credential, or reusable OAuth artifact is written to a user/runtime profile.
4. Replacing, disconnecting, removing, restoring, expiring, or changing payer authority revokes prior generations before new authority becomes active.
5. `missing`, `sealed`, `corrupt`, `unavailable`, and `ok` are distinct observable states. None collapses silently to an empty string.
6. Credential publication is resumable and idempotent across process interruption.
7. Malformed metadata fails visibly and is never rewritten from an empty fallback.
8. Host/root compromise is outside the non-retrieval claim and must be stated explicitly in public security documentation.

## Authority classes

### Vault-backed API credentials

API keys and other static provider secrets remain envelope-encrypted in the Workframe vault. Runtime profiles receive only opaque, revocable Workframe capability material.

### Hermes-native OAuth credentials

The current OAuth path copies provider fields such as `access_token` and `refresh_token` into runtime `auth.json`. That path violates the runtime-file invariant and is in scope for this rail.

- OAuth callback/device completion must store reusable provider authority in the server-side vault or an equally narrow server-owned encrypted record.
- Runtime `auth.json` may contain provider identity, account label, expiry metadata, and an opaque Workframe capability reference, but no reusable upstream token.
- The broker/proxy path must present or refresh OAuth authority server-side for the exact provider operation.
- Refresh rotation must advance capability generation and revoke prior leases before the replacement becomes active.
- Legacy runtime OAuth material must be detected, migrated or quarantined, scrubbed from the runtime file, and never silently re-published.
- Providers that cannot currently operate through a server-side broker must fail closed as `oauth_broker_unsupported`; they are not exempted by writing tokens back to disk.

## Minimum durable lifecycle

```text
staged → bound → published → active
                    ↘ failed
active → rotating → active
active → revoked
```

Use the existing Workframe database, vault, OAuth/provider binding records, and lease tables. Prefer additive columns/tables and small functions over a new framework. A lifecycle transition must be committed before external/runtime side effects and reconciled afterward.

## Required implementation

- introduce a typed provider-authority read result with explicit status and a compatibility wrapper only where legacy callers still require one;
- make proxy/lease resolution consume the typed result and return a nonsecret typed failure;
- persist capability generation and lifecycle state for credential bindings, including OAuth-backed bindings;
- bind every issued lease to the current generation and reject stale generations;
- on replacement/revoke/refresh, advance generation and revoke matching leases before publishing the replacement;
- migrate or quarantine reusable OAuth authority currently stored in runtime `auth.json`, then scrub it from runtime files;
- make auth metadata parsing fail closed without erasing existing content;
- add recovery that resumes or marks interrupted `staged`, `bound`, `published`, and `rotating` operations;
- document the trust model as non-retrievable through normal product authority, explicitly excluding host/root compromise and process-memory inspection.

## Acceptance matrix

- successful user API-key credential store/use;
- successful workspace API-key credential store/use;
- successful OAuth connect, refresh, use, disconnect, and legacy-token migration without reusable tokens in runtime files;
- interruption after vault/OAuth authority write, binding write, lease revoke, runtime capability publication, provider refresh, and final activation;
- replacement or OAuth refresh while an old lease is active;
- provider disconnect, member removal, role downgrade, workspace deletion, agent deletion, payer change, expiry, and restore;
- sealed vault, missing row, malformed ciphertext, wrong KEK, unavailable vault DB, malformed auth metadata, unsupported OAuth broker, and corrupt legacy OAuth material;
- raw-authority scan over API responses, profile/runtime files, logs, receipts, test artifacts, package artifacts, and backups;
- explicit test proving the claim does not include host/root/process-memory compromise.

Every failure test asserts unchanged or explicitly recoverable database/filesystem state.

## Non-goals

- no admin plaintext recovery;
- no claim against host/root compromise or malicious code executing inside the API process;
- no local-device-only BYOK adapter in this rail;
- no provider catalog redesign;
- no runtime-binding/port redesign—that is WF-049;
- no HTTP parser work—that is WF-050.

## Completion

Code-complete requires deterministic API-key and OAuth interruption/revocation tests, legacy runtime-token migration tests, a raw-authority scan, precise trust-model documentation, and green existing credential, provider, profile, install, and package suites. Public-beta completion still depends on the target-cell restore/revocation matrix in WF-046.
