# WF-048 — Capability-based credential lifecycle

## Purpose

Workframe may use provider authority without exposing the upstream secret to a browser, user, workspace admin, stack operator, agent profile, normal product API, log, receipt, or runtime file.

The current envelope-encrypted vault and opaque lease design is the correct base. This rail tightens it; it does not replace it with crypto theater, a new secret manager, blockchain, MPC, enclaves, or a local-only architecture.

## Invariants

1. One credential binding ID owns one vault secret and one monotonically increasing capability generation.
2. A raw secret is decrypted only inside the outbound provider request path and is never returned as product data.
3. Runtime files contain opaque capability material and nonsecret provider metadata only.
4. Replacing, disconnecting, removing, restoring, expiring, or changing payer authority revokes prior generations before new authority becomes active.
5. `missing`, `sealed`, `corrupt`, `unavailable`, and `ok` are distinct observable states. None collapses silently to an empty string.
6. Credential publication is resumable and idempotent across process interruption.
7. Malformed metadata fails visibly and is never rewritten from an empty fallback.

## Minimum durable lifecycle

```text
staged → bound → published → active
                    ↘ failed
active → rotating → active
active → revoked
```

Use the existing Workframe database, vault, and lease tables. Prefer additive columns/tables and small functions over a new framework. A lifecycle transition must be committed before external/runtime side effects and reconciled afterward.

## Required implementation

- introduce a typed vault read result with explicit status and a compatibility wrapper only where legacy callers still require one;
- make proxy/lease resolution consume the typed result and return a nonsecret typed failure;
- persist capability generation and lifecycle state for credential bindings;
- bind every issued lease to the current generation and reject stale generations;
- on replacement/revoke, advance generation and revoke matching leases before publishing the replacement;
- make auth metadata parsing fail closed without erasing existing content;
- add recovery that resumes or marks interrupted `staged`, `bound`, `published`, and `rotating` operations;
- document the trust model as non-retrievable least privilege, not mathematical zero knowledge.

## Acceptance matrix

- successful user credential store/use;
- successful workspace credential store/use;
- interruption after vault write, binding write, lease revoke, runtime publication, and final activation;
- replacement while old lease is active;
- provider disconnect, member removal, role downgrade, workspace deletion, agent deletion, payer change, expiry, and restore;
- sealed vault, missing row, malformed ciphertext, wrong KEK, unavailable vault DB, and malformed auth metadata;
- raw-secret scan over API responses, profile files, logs, receipts, and test artifacts.

Every failure test asserts unchanged or explicitly recoverable database/filesystem state.

## Non-goals

- no admin plaintext recovery;
- no local-device-only BYOK adapter in this rail;
- no provider catalog redesign;
- no runtime-binding/port redesign—that is WF-049;
- no HTTP parser work—that is WF-050.

## Completion

Code-complete requires deterministic interruption/revocation tests and green existing credential, provider, profile, install, and package suites. Public-beta completion still depends on the target-cell restore/revocation matrix in WF-046.
