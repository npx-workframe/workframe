# Philosophical and Reasoning Model

## 1. Purpose

Workframe Origin is not a neutral form generator. It is a guided formation system that helps a human and an authorized agent establish enough durable context to collaborate coherently.

The process begins with philosophical dependency order, not package order or folder order. The campaign's formation sequence is:

```text
teleology
  -> ontology
  -> epistemology
  -> axiology and doctrine
  -> identity and authority
  -> constitution and governance
  -> praxeology and project structure
  -> knowledge, skills, agents, and models
  -> work coordination and execution
  -> meta, audit, and upkeep
```

Architectonic storage layers do not need to mirror this list one-for-one. For example, the current `doctrine` layer may hold declared purpose and general decision rules, while `constitution` holds invariants and authority boundaries. The formation order describes how understanding is established; Architectonic profiles describe where durable concerns are stored.

## 2. Teleology — to what end?

Teleology is first because structure without purpose produces confident organization of the wrong thing.

The system must establish:

- what the user is trying to create, preserve, change, understand, or operate;
- who benefits;
- why the effort matters;
- what success looks like;
- what must not result;
- which outcome matters now when several goals compete;
- the relevant time horizon;
- whether the need is durable enough to justify installation at all.

The first classification may be multi-select:

```text
start an organization
start a business
start a project
build a personal knowledge system
form an agent team
understand or organize existing work
something else
```

This is not yet ontology. “Start a business” is an intention. Later stages determine whether the durable entity is one organization, several projects, a sole practice, a knowledge system, or another form.

### Teleological completion condition

The system can state, in language the user accepts:

```text
This exists to <produce or preserve outcome>
for <beneficiaries>
under <material constraints>
and success is evidenced by <observable conditions>.
```

It may preserve unresolved alternatives rather than force one false objective.

## 3. Ontology — what exists?

Ontology determines which entities and relationships are real enough to receive durable names and boundaries.

Candidate concepts include:

- human;
- user;
- owner;
- organization;
- business;
- team;
- role;
- agent;
- project;
- repository;
- workspace;
- product;
- service;
- customer or beneficiary;
- source;
- knowledge domain;
- system;
- asset;
- process;
- external authority;
- private zone.

The system must not infer that every folder is a project, every repository is a product, every person named in a document is a user, or every business activity belongs to one organization.

### Ontological questions

- Is this one entity or several related entities?
- Which projects belong to which organization?
- Is a repository the project, one component of it, or merely a source?
- Which material belongs to the person, the organization, a client, or a separate professional role?
- Which actors are human, software, institutional, contractual, or external?
- Which boundaries must remain separate even when the same person owns both sides?

### Ontological completion condition

The system has an accepted entity map with stable identifiers, ownership, containment or association relationships, and explicit unresolved classification questions.

## 4. Epistemology — what is known, and how?

Epistemology determines how claims enter, remain, change, or leave the durable system.

The system distinguishes:

| Knowledge state | Meaning |
|---|---|
| **Fact** | Supported by a recoverable source within its stated scope. |
| **Decision** | An explicit chosen direction with owner, date, scope, rationale, and status. |
| **Assumption** | A provisional claim used without adequate evidence. |
| **Inference** | A model or human interpretation derived from evidence but not directly stated by it. |
| **Unknown** | A recognized missing answer that must not be filled by guesswork. |
| **Contradiction** | Two or more claims cannot all govern in the same scope and time. |
| **Stale claim** | A formerly supported claim whose source or validity may no longer be current. |
| **Superseded decision** | A prior decision replaced by a later explicit decision. |
| **Temporary context** | Session state, mood, shorthand, or provisional working material that should not become canonical. |
| **Sensitive source** | Material whose access, processing, transmission, or retention requires special restrictions. |

### Source authority

A source can be readable without being authoritative. The system records:

- source owner;
- source type;
- recoverability;
- observed date;
- source-modified date;
- scope;
- authority status;
- conflicts;
- sensitivity;
- processing grants;
- staleness policy.

### Epistemological rules

1. Explicit source material outranks model memory.
2. Accepted current source material outranks derived summaries.
3. A user may make a decision, but a decision does not retroactively make every supporting claim factual.
4. Access does not confer authority.
5. Retrieval relevance is not evidence.
6. Generated prose is a proposal until accepted and written through a validated transaction.
7. Unknowns are first-class objects.
8. Contradictions are preserved until resolved by an authorized actor or scoped by time/context.
9. Private raw material should remain at its source when an index or extract is sufficient.
10. The agent must state uncertainty before relying on it.

### Epistemological completion condition

The system knows which sources govern the current formation scope, how claims are classified, how contradictions are resolved, and which material remains unknown or excluded.

## 5. Axiology and doctrine — what is valued and how should judgment work?

Doctrine records the decision rules that should guide behavior when facts alone do not determine an action.

It may include:

- declared purpose;
- values and priorities;
- trade-off rules;
- evidence standards;
- user experience principles;
- incentives and anti-incentives;
- risk posture;
- method;
- criteria for escalating or stopping;
- rules for when not to build, automate, publish, or act.

The system should avoid generic values pages. It should derive questions from decisions and contradictions.

Example:

```text
Your public material calls accessibility a core principle, but the current
product plan contains no accessibility requirements. Is accessibility:

1. a non-negotiable invariant,
2. a prioritized principle with explicit trade-offs,
3. an aspiration not yet operationalized, or
4. outdated language?
```

### Doctrine completion condition

The system can explain how the entity should make recurring judgment calls and where the user has deliberately left discretion.

## 6. Identity and authority — who may do what?

Identity in this system is collaboration-relevant, not biographical surveillance.

The durable model may include:

- humans and organizations;
- roles and responsibilities;
- agents and runtime profiles;
- ownership;
- decision authority;
- approval authority;
- delegation and subdelegation;
- access rights;
- mutation rights;
- publishing and communication rights;
- spending authority;
- override and stop authority;
- privacy boundaries;
- conflicts of interest;
- escalation routes.

### Core distinction

```text
identity file       describes an actor or role
permission grant    allows a capability within a scope
runtime binding     connects an installed agent to an executing process
```

None implies the others.

### Identity and authority completion condition

Every installed operational agent has a human owner, a scope, explicit capabilities, prohibited actions, approval gates, and a stop authority. Material human roles and organizational boundaries are named without unnecessary private biography.

## 7. Constitution and governance — what must remain true?

The constitution stores invariants and amendment rules that should survive changing projects, models, personnel, and tactics.

Candidate concerns:

- human authority root;
- non-negotiable prohibitions;
- protected privacy zones;
- required approvals;
- authority to amend doctrine or constitution;
- emergency stop and override;
- separation of personal and organizational domains;
- rules for agent creation and delegation;
- destructive-change boundaries;
- legal or regulatory constraints explicitly adopted by the user;
- composition rules between independently owned concerns.

The system must not claim that a constitution makes the system lawful, safe, or correct. It makes declared boundaries inspectable.

### Constitution completion condition

The minimum invariants, authority root, prohibited actions, approval boundaries, and amendment rules are explicit enough that an agent can recognize when it must stop or escalate.

## 8. Praxeology and project structure — how does purposeful action become bounded work?

A project is a bounded operating unit, not necessarily a repository and not necessarily subordinate to an organization.

The project layer should establish:

- purpose and outcome;
- scope and exclusions;
- users or beneficiaries;
- canonical sources;
- current architecture or state;
- decisions;
- assumptions;
- risks;
- open questions;
- success and verification conditions;
- relationship to repositories and source attachments;
- handoff and reconciliation rules.

### Rail decision

The system asks whether work must survive:

- session boundaries;
- multiple roles or agents;
- dependencies;
- review;
- approval;
- external scheduling;
- durable ownership claims.

When yes, bind exactly one Rail ledger. When no, do not manufacture process infrastructure.

### Project completion condition

The project can be entered by a new authorized agent without relying on chat history, and the agent can identify the canonical sources, current objective, constraints, unknowns, and—when present—the single Rail.

## 9. Knowledge, skills, agents, and models

### Knowledge

Knowledge organizes disclosed claims, sources, evidence, uncertainty, contradictions, and known unknowns. It remains canonical independently of retrieval technology.

### Skills

Skills are repeatable procedures with triggers, inputs, steps, verification, and failure modes. Discovery of a skill does not authorize its execution.

### Agents

Agents are installed local actors composed from:

- archetype;
- purpose;
- owner;
- project/organization scope;
- runtime;
- model policy;
- skills;
- knowledge attachments;
- tools;
- grants;
- budgets;
- review and escalation.

### Models

Model policy is dated and replaceable. It may specify capabilities, cost limits, privacy constraints, fallback behavior, and task suitability. Model availability does not define ontology.

### Completion condition

The system contains only the knowledge, skills, agents, and model policies justified by recurring needs. Each attachment has provenance, trust status, and authority boundaries.

## 10. Execution and Workframe

Workframe makes the durable system operational through:

- users and roles;
- rooms and Spaces;
- agent routes and profiles;
- sessions;
- files;
- runtime credentials and leases;
- runs;
- approvals;
- artifacts;
- Rail views;
- activity and evidence.

Architectonic remains the durable contract. Workframe remains an execution and collaboration surface. Runtime session history remains runtime state, not the highest source of truth.

## 11. Meta, audit, and upkeep

Any durable system can decay. The meta stage defines:

- who maintains the system;
- review cadence or trigger;
- staleness rules;
- contradiction review;
- source retirement;
- agent and permission audit;
- model-policy review;
- Rail hygiene;
- backup and restore;
- stop conditions;
- when living knowledge is justified;
- how the system may simplify itself.

The default is deliberate curation. Living-knowledge loops are added only when external change can make the corpus wrong independently of local edits and when watch boundaries, cadence, verification, publication gates, budgets, and stop conditions are explicit.

## 12. Deterministic and probabilistic responsibility

### 12.1 Deterministic engine owns

- command parsing;
- runtime and provider detection;
- filesystem scope enforcement;
- permission grants and revocation;
- secret input and storage;
- file inventories and hashes;
- ignored-path rules;
- schema validation;
- Architectonic layer dependency resolution;
- target path selection;
- exact file destinations;
- diff generation;
- backups and checkpoints;
- atomic writes where possible;
- installation commands;
- repository clone/adopt/mount mode;
- Rail uniqueness;
- runtime profile creation;
- Workframe deployment;
- verification;
- receipts and audit logs;
- failure recovery.

### 12.2 Probabilistic model owns

- interpreting natural-language answers;
- semantic source classification;
- candidate entity recognition;
- contradiction detection;
- identifying likely stale or superseded claims;
- ranking unresolved questions by consequence;
- explaining trade-offs;
- drafting doctrine;
- proposing project boundaries;
- suggesting relevant Architectonic concerns;
- summarizing authorized sources;
- recognizing that an answer is ambiguous or incomplete.

### 12.3 Probabilistic model may not own

- authorization;
- secret discovery;
- unrestricted path selection;
- arbitrary shell commands;
- file mutation;
- package installation;
- runtime privilege;
- spending;
- external communication;
- deletion;
- claims of fact without evidence;
- final resolution of authority conflicts.

### 12.4 Hybrid decision contract

Every model-derived proposal follows:

```text
bounded evidence
  -> model proposal
  -> provenance attachment
  -> deterministic schema validation
  -> authority and permission check
  -> user confirmation when consequential
  -> deterministic transaction
  -> read-back verification
```

## 13. Question value model

Candidate questions may be scored by deterministic and probabilistic factors:

```text
value = consequence
      × unresolved_confidence
      × durable_relevance
      × answerability
      × authorized_evidence_support
      - redundancy
      - privacy_cost
      - user_burden
      - premature_detail
```

The numeric implementation is optional. The behavioral requirement is not: ask the question whose answer most improves safe, useful continuity at the current stage.

## 14. Anti-patterns

- Asking “What are your values?” before reviewing available evidence.
- Treating a folder list as an ontology.
- Saving answers as isolated fields without updating durable documents.
- Generating a complete organization because the user selected “business.”
- Inferring identity from private files without explicit purpose and consent.
- Recording a model summary as a fact.
- Hiding contradictions to present a clean setup score.
- Creating multiple boards, queues, and task files that compete with Rail.
- Equating a configured API key with permission to spend.
- Binding an agent to every repository because it can see them.
- Making the user explain information that authorized documents already contain.
- Using a model for deterministic parsing or path validation merely because it is available.
- Forcing a Workframe deployment when files alone solve the durable-context problem.

## 15. Completion doctrine

Formation is complete enough to operate when:

- the current purpose is explicit;
- the material entities and project boundaries are accepted;
- source and knowledge policy is defined;
- authority root and prohibitions are explicit;
- privacy and access scopes are recorded;
- at least one useful project or knowledge outcome exists;
- important contradictions are resolved or preserved;
- each Rail-enabled project names one ledger;
- each installed agent has owner, scope, permissions, and stop authority;
- canonical files verify;
- runtime and Workframe bindings verify when installed;
- the next session can load the correct context without reconstructing it from chat.

Completeness is not the absence of unknowns. It is the presence of enough explicit purpose, evidence, boundaries, and current work to proceed without pretending.
