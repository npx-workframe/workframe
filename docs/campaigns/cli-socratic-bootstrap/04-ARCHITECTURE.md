# Architecture

## 1. Architectural objective

Workframe Origin must convert an unknown local environment into a verified, user-owned collaboration system without confusing discovery, inference, authority, mutation, and execution.

The architecture therefore separates five planes:

```text
1. discovery plane    what is present
2. authority plane    what may be inspected, transmitted, changed, or executed
3. formation plane    what the evidence and user decisions mean
4. persistence plane  where durable doctrine and work state live
5. execution plane    which agents and runtimes may act through Workframe
```

No plane may silently substitute for another. A detected runtime is not authorized. A readable file is not authoritative. A model inference is not a fact. An installed agent is not empowered. A successful process is not proof of correct doctrine.

## 3. Components

### 3.1 CLI shell and renderer

Responsibilities:

- command parsing;
- terminal capability detection;
- simple, accessible, and expert rendering modes;
- one-question-at-a-time presentation;
- keyboard-only operation;
- progress, pause, resume, explain, undo, and exit controls;
- safe secret input without echo;
- consistent display of evidence, inference, consequence, and proposed action.

The renderer does not own business rules, permissions, or file mutations.

### 3.2 Discovery engine

The discovery engine performs allowlisted, read-only probes. It contains independent probe modules for:

- host platform and architecture;
- shells and package managers;
- Git and repository roots;
- Docker and local deployment substrates;
- supported runtime executables;
- safe runtime authentication-status commands;
- provider environment-variable presence;
- existing Architectonic manifests;
- existing Workframe instances;
- user-approved path inventories;
- file metadata and content extraction.

Each probe returns a typed result and evidence receipt:

```text
probe id
probe version
scope
command or filesystem method
started_at / completed_at
status
redacted observations
errors
mutation assertion
```

The engine must not improvise commands generated by a model.

### 3.3 Consent authority

The consent authority is the canonical source for grants. It owns:

- requested capability;
- exact scope;
- purpose;
- data class;
- local or external processing;
- permitted adapter or process;
- mutation level;
- expiry;
- revocation;
- parent grant;
- audit history.

Example capabilities:

```text
host.runtime_inventory
filesystem.list_roots
filesystem.inventory:/Users/maria/Projects
filesystem.read:/Users/maria/Projects/course
filesystem.write:/Users/maria/Workframe
inference.use:claude-cli
inference.transmit:source-excerpts
credential.store:openrouter
repository.clone:github.com/example/course
workframe.deploy:local_single_user
```

Consent is never represented only by conversational text. A natural answer is interpreted, then compiled into an explicit grant that the user can review.

### 3.4 Runtime and provider adapter registry

The adapter registry normalizes existing intelligence paths.

```text
RuntimeAdapter
  id
  display_name
  discovery
  auth_probe
  invocation_modes
  sandbox_controls
  file_access_model
  network_behavior
  cancellation
  receipt_capture
  cost_disclosure
  limitations

ProviderAdapter
  id
  environment_markers
  secure_key_input
  vault_binding
  request_adapter
  model_allowlist
  budget_controls
  usage_receipts
```

#### Use-in-place rule

Authenticated CLI sessions should be invoked through their supported interface. Workframe Origin must not copy or parse private session tokens merely to centralize them.

#### User-key rule

Keys explicitly supplied by the user may be stored in the Workframe vault or another approved secret store. Environment variables may be used in place after consent without exposing values.

#### Hosted fallback rule

A Workframe-funded fallback must be a server-side relay, never a distributed shared API key. It requires session authorization, model allowlists, strict budgets, rate limits, abuse controls, and clear funding disclosure.

### 3.5 Progressive scanner

The scanner is not a whole-disk crawler. It operates through levels:

```text
L0  no filesystem access
L1  user-selected roots only
L2  folder/repository names and metadata
L3  file inventory and metadata
L4  selected content extracted locally
L5  selected excerpts approved for external inference
L6  approved attachment or mutation
```

Each level requires the corresponding grant. The scanner supports:

- ignore files and standard repository excludes;
- hidden-file policy;
- size and count budgets;
- file-type allowlists;
- binary detection;
- archives disabled by default;
- symlink and junction handling;
- cloud-placeholder detection;
- read errors without privilege escalation;
- sensitive-path heuristics that stop and ask rather than continue;
- content hashing for provenance without retaining raw copies where unnecessary.

### 3.6 Evidence inventory

The evidence inventory stores references and classifications, not an uncontrolled archive.

```text
EvidenceItem
  id
  source_uri
  attachment_id
  path_label
  content_hash
  observed_at
  source_modified_at
  source_type
  authority_status
  sensitivity
  processing_scope
  extracted_claims[]
  contradictions[]
  staleness
```

Raw private material remains at the source unless the user explicitly selects a copy or import mode.

### 3.7 Formation orchestrator

The orchestrator owns the resumable Socratic process. It does not use a single long system prompt as hidden state. It loads:

- current formation stage;
- relevant accepted doctrine;
- authorized evidence subset;
- unresolved contradictions and unknowns;
- prior explicit answers;
- question history;
- grants;
- proposed and applied changes.

Question selection is constrained by a deterministic stage contract and a probabilistic semantic ranking. The model proposes candidate questions; the orchestrator validates that the question:

- belongs to the current or justified earlier stage;
- is not already answered by accepted sources;
- names the evidence or gap;
- has a durable write target;
- does not request unauthorized information;
- does not imply authority from access;
- is not redundant;
- has an explainable consequence.

### 3.8 Philosophical stage contracts

Each formation stage has:

```text
stage id
purpose
required inputs
allowed evidence classes
candidate concepts
minimum completion conditions
valid write targets
questions that must not be asked
transition conditions
```

The formation sequence is defined in `05-PHILOSOPHICAL-AND-REASONING-MODEL.md` and instantiated in `06-SOCRATIC-SCRIPT.md`.

### 3.9 Architectonic planner and compiler

The planner receives accepted durable concerns and selects the smallest justified Architectonic closure.

```text
concern set
  -> deterministic layer recommendation
  -> dependency closure
  -> proposed local document map
  -> source attachment map
  -> project and Rail bindings
  -> agent and authority bindings
```

The compiler converts accepted structured records and approved prose into files. It must:

- validate path boundaries;
- refuse silent overwrite;
- generate diffs;
- create backups or checkpoints;
- distinguish upstream package files from local user-owned files;
- attach provenance;
- validate manifests and schemas;
- support dry run;
- apply atomically where the filesystem permits;
- record partial failure and recovery steps.

A model may draft prose. It may not choose arbitrary destinations or execute shell mutations.

### 3.10 Source attachment manager

The attachment manager preserves the difference between the user's existing world and the generated system.

Supported modes:

| Mode | Behavior | Intended use |
|---|---|---|
| `reference` | Store a pointer only. | External system or source not needed in workspace filesystem. |
| `adopt_existing_repository` | Bind an existing checkout in place. | User already has a canonical local repo. |
| `clone_repository` | Clone into an approved workspace path. | Remote repo has no local checkout or user wants an isolated copy. |
| `mount_read_only` | Expose a directory without mutation authority. | Research, archives, sensitive sources, or shared folders. |
| `mount_read_write` | Expose and permit validated writes. | Active project workspace explicitly delegated to agents. |
| `copy_snapshot` | Copy selected files and record origin and hash. | Frozen evidence or migration snapshot. |
| `import_extract` | Persist selected excerpts or normalized records. | Large, remote, or sensitive sources where raw material should not be copied. |

Each attachment records refresh policy, authority, sensitivity, and ownership. The system must never silently convert a reference into a copy or a read-only mount into write access.

### 3.11 Project and Rail manager

The project manager separates project, repository, workspace, and organization.

```text
organization
  ├─ project A
  │    ├─ repository 1
  │    ├─ repository 2
  │    ├─ source attachments
  │    └─ one optional Rail
  └─ project B
       ├─ non-code folders
       └─ one optional Rail
```

Rail is installed only when durable work selection must cross sessions, roles, dependencies, review, or approval. The manager validates exactly one `ledger_root` per Rail-enabled project and treats backlog, queue, now, board, and status as views rather than parallel authored authorities.

### 3.12 Agent binder

The agent binder composes installed-agent records from Architectonic archetypes, local doctrine, permissions, skills, knowledge attachments, and runtime adapters.

An agent binding is incomplete unless it names:

- human owner and stop authority;
- purpose and role;
- organization and project scope;
- runtime profile;
- model and funding policy;
- filesystem grants;
- tool and external-action grants;
- spending limits;
- required approvals and independent review;
- Rail access and selection rule;
- evidence and handoff requirements;
- escalation path;
- kill condition.

### 3.13 Workframe deployment adapter

The deployment adapter does not reimplement Workframe. It plans and invokes an approved Workframe installation or attaches the Architectonic instance to an existing workspace.

Modes:

```text
repository_only
local_single_user
local_trusted_team
attach_existing_workframe
remote_new_deployment   # later, separate public-deploy gate
```

The adapter maps:

- Architectonic actors to Workframe users and roles;
- installed agents to Workframe routes/profiles;
- projects to rooms, Spaces, file roots, and Rail views;
- source attachments to workspace file access;
- credentials to vault entries and runtime leases;
- authority rules to approvals and action gates;
- model policy to runtime profiles;
- current work to project Rail views.

### 3.14 Verification engine

Verification runs at four levels:

1. **Structural:** files, manifests, schemas, dependency closure, unique Rail roots.
2. **Authority:** every runtime, source, agent, and mutation has a valid grant and owner.
3. **Operational:** runtime invocation, Workframe health, session binding, file access, Rail selection.
4. **Narrative:** generated entry points accurately route agents to canonical sources and do not overstate certainty.

## 4. Data flow

### 4.1 Discovery without model use

```text
user starts CLI
  -> deterministic host probes
  -> redacted status report
  -> no mutation
  -> no network inference
```

### 4.2 Authorized semantic inspection

```text
user grants inventory access
  -> scanner indexes metadata locally
  -> user selects candidate sources
  -> local extraction and redaction
  -> user grants external processing for exact excerpts
  -> inference adapter receives bounded context
  -> model returns classifications and candidate questions
  -> deterministic validator records them as proposals
```

### 4.3 Doctrine write

```text
accepted evidence + explicit answer
  -> model drafts proposed doctrine fragment
  -> schema and source validation
  -> user reviews material consequence
  -> compiler produces exact diff
  -> transaction engine writes
  -> verification reads back
  -> formation checkpoint advances
```

### 4.4 Agent run after installation

```text
user opens project in Workframe
  -> Workframe resolves user, room, agent, and runtime profile
  -> project entry point loads purpose, authority, sources, and Rail
  -> vault issues bounded lease when required
  -> runtime executes with project grants
  -> artifacts and evidence return to Workframe
  -> accepted durable result is reconciled into files
  -> Rail receives one validated state transition
```

## 5. Trust boundaries

### Boundary A — User and bootstrapper

The user authorizes capabilities. Natural-language consent is translated into explicit grants and shown back for confirmation when sensitive.

### Boundary B — Bootstrapper and local filesystem

The scanner and compiler use OS-level permissions plus internal scope validation. Filesystem readability does not imply allowed inspection.

### Boundary C — Bootstrapper and external model

Only approved excerpts may leave the machine. The request receipt records adapter, provider, model, data classes, and source IDs.

### Boundary D — Workframe vault and runtime

Raw secrets remain in the vault. Runtime profiles receive leases or use existing CLI authentication in place. General internet use and secret-mediated provider actions remain distinct.

### Boundary E — Architectonic system and source attachments

Canonical doctrine may cite or attach external sources, but source ownership and location remain explicit. Generated summaries never silently replace originals.

### Boundary F — Installed agent and operational authority

Agent files describe a role; runtime grants determine actual capability. Workframe enforces user/project scope and approval boundaries.

## 7. Deployment topology

### Repository-only

Architectonic files and project attachments are created. No Workframe services run. Existing CLI agents can consume the generated entry points.

### Local single user

Workframe UI/API and one or more runtimes operate on the same machine. The user is the authority root. Vault and local profiles isolate credentials.

### Local trusted team

A small known team shares a Workframe instance with per-user profiles, explicit project membership, and organization/project permissions.

### Remote or public multi-user

This is a separate deployment gate. It requires HTTPS, authentication, vault keys, SMTP or equivalent identity delivery, backup posture, invite policy, supervisor isolation, brokered secrets, and public threat-model verification. It must not be inferred merely because Docker and a VPS are available.

## 8. Transaction model

Every mutating operation follows:

```text
proposal
  -> scope and authority validation
  -> exact plan
  -> user approval when required
  -> checkpoint or backup
  -> apply
  -> read-back verification
  -> receipt
  -> state transition
```

Operations are idempotent where possible. Partial execution records the last verified step and recovery instructions. Existing directories cause `reopen`, `adopt`, `repair`, or explicit `replace` branches; they never route to silent scaffold overwrite.

## 9. Runtime-neutral startup contract

Every authorized runtime receives an adapter-specific wrapper around the same conceptual startup context:

```text
actor identity
human owner
organization and project
purpose and current objective
canonical read order
knowledge and source boundaries
permissions and prohibitions
model/funding policy
one Rail root when present
work-selection rule
verification and handoff contract
```

Claude instructions, Codex repository instructions, Hermes profiles, Pi prompts, or future runtime formats are adapters. They must not become competing sources of doctrine.

## 10. Architectural invariants

- No model call before inference authorization.
- No file-content inspection before content authorization.
- No external transmission merely because local read access exists.
- No secret scraping.
- No whole-disk content scan by default.
- No silent path overwrite.
- No generated claim promoted to fact without evidence or explicit user acceptance.
- No project ontology inferred solely from filenames.
- No duplicate live-work authority within a project.
- No installed agent without owner, scope, and stop authority.
- No runtime adapter allowed to bypass project permissions.
- No chat transcript treated as canonical doctrine.
- No Workframe deployment required when a repository-only outcome satisfies the goal.
- No permanent dependence on a hosted Workframe service or specific model provider.
